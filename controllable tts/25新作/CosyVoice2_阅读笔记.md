# CosyVoice 2: 可扩展的流式语音合成

- **来源**: arXiv:2412.10117
- **作者**: Zhihao Du, Qian Chen, Xian Shi, etc. (阿里 FunAudioLLM 团队)
- **发表**: arXiv 2024

---
## 1. 研究背景与问题

大模型做 TTS 的致命问题——慢。

更具体地说：
**自回归推理的天生瓶颈**：LLM 生成第 N 个 token 必须等前 N-1 个都生成完。语音 token 序列动辄几百上千个 token，逐个生成的延迟累积起来远超实时要求。
**非自回归方案的质量损失**：有些工作放弃自回归，用扩散或 CTC 直接预测整段语音。==无法做零样本说话人克隆==——因为克隆需要参考音频逐帧对齐，非自回归框架不太擅长。
**流式与非流式的割裂**：实际应用需要流式（边生成边播放），但 LLM 的因果注意力机制要求看完整上下文。强行截断上下文会破坏生成质量。

- [?] 这个问题确实是 LLM-based TTS 走向实用的核心障碍

CosyVoice 2 的回答：==不改自回归框架，改注意力的看法==。用"块级因果注意力"让 LM 按固定大小的块生成，每生成一块就送下游，实现流式推理。

## 2. 方法概述

### 2.1 整体架构
![[Pasted image 20260412215103.png|654]]
**语音分词器**：==基于 SenseVoice 的语义编码器 + FSQ（Finite Scalar Quantization）==。每帧输出 2 个 token，码本大小 16384。相比 CosyVoice 1 代用的 VQ，FSQ 解决了码本坍缩问题，且每帧信息密度更高。

**统一 LM**：Qwen2.5-0.5B，文本和语音共享词表。所有任务（TTS、克隆、指令控制）通过不同的 prompt 模板区分，模型本身不知道自己在做哪个任务。

**流匹配（Flow Matching）**：把离散 token 映射回连续梅尔谱。用 Conditional Flow Matching，4 步 ODE 推理。

**流式声码器**：HiFi-CN，支持逐块输入逐块输出。

### 2.2 块级因果注意力——流式推理的关键
1. **非流式处理 (Non-Streaming Processing)**
- **核心定义**：模型在处理前必须获取完整的输入序列（**即全局上下文**），随后一次性或连续地生成完整的输出序列。
- **序列构造特征**：`<Start> + [完整输入文本] + <Turn> + [完整输出语音/目标序列] + <End>`。
- **局限性**：高延迟。用户必须等待整个输入序列接收完毕且模型处理完成，无法满足实时交互场景（如实时语音助手）的需求。
    
1. **流式处理 (Streaming Processing)**
- **核心定义**：增量式的数据处理与输出。系统在仅接收到部分输入（**局部上下文**）时即可启动生成过程，实现“边接收边生成”。
    
- **序列构造特征（基于交替混合机制）**：将输入与输出序列按照预设的固定比例（如 $N:M$）进行交替拼接。例如，每输入 $N$ 个文本 Token，模型必须生成相应的 $M$ 个语音 Token。
    
- **关键同步机制 (Filling Token 策略)**：现代范式引入了特殊的占位符（如 Filling Token）。当模型在推理时预测当前块的文本已耗尽，它会主动输出该 Token 作为一个显式的“请求信号”，指示外部系统送入下一批增量文本。下一批文本结合之前的 text + speech token 自回归建模。
- **局限性**：由于缺乏未来的文本信息（如句末的反问语气或突然的情感转折），模型更容易出现语调平淡或局部解析错误。

这是 CosyVoice 2 最核心的技术贡献。传统因果注意力要求每个 token 只能看它前面的所有 token：

```
传统因果注意力（完整序列才能输出）：

t1 → t2 → t3 → t4 → t5 → t6 → ... → tN
|    |    |    |    |    |              |
v    v    v    v    v    v              v
[必须等全部生成完才能送声码器]
```

CosyVoice 2 改成按块处理：

```
块级因果注意力（每块生成立即送下游）：

[t1 t2 t3] → [t4 t5 t6] → [t7 t8 t9] → ...
  块1          块2          块3
   |            |            |
   v            v            v
 Flow+Vocoder  Flow+Vocoder  Flow+Vocoder
   |            |            |
   v            v            v
 音频块1      音频块2      音频块3
 (立即播放)   (立即播放)   (立即播放)
```

具体实现：
- **左块（Left Chunk）**：当前块可以 attend 到前面所有已生成的块（保证质量）
- **右块（Right Chunk）**：当前块不能 attend 到后面的块（保证因果性）
- **块大小**：通过调节块大小权衡延迟和质量——块越小延迟越低但质量可能下降

关键发现：==块大小设为 25 帧（约 400ms 音频）时，流式模式和非流式模式的音质差异已经很小==。

### 2.3 FSQ vs VQ

CosyVoice 2 选择了 FSQ（Finite Scalar Quantization）替代传统的 VQ（Vector Quantization）：

| 方面 | VQ | FSQ |
|------|-----|-----|
| 码本维护 | 需要 EMA 更新 | 无需维护码本 |
| 码本坍缩 | 常见（部分码本向量闲置） | 不会发生 |
| 每帧 token 数 | 通常 4-8 个码本 | 2 个（低码率） |
| 实现复杂度 | 较高 | 较低 |

FSQ 的原理更直觉：把连续向量的每个维度独立量化到固定范围（如 [-1, 0, 1]），然后拼接编码。不需要学习码本，不会坍缩。

### 2.4 训练策略

两阶段训练：

**阶段一：预训练**
- 大规模无标注语音数据
- 目标：让 LM 学会语音 token 的分布规律

**阶段二：有监督微调（SFT）**
- 构造"文本+指令 → 语音"的配对数据
- 教模型根据文本和指令生成特定语音
- 包含零样本克隆、跨语言合成、指令控制等多种任务的混合数据

>[!important]
>CosyVoice 2 没有采用 RLHF/DPO 或模型合并等后训练策略。模型合并的描述是错误的——论文的训练流程就是预训练 + SFT 两阶段。后训练策略（IFT + DPO）是到 CosyVoice 3 才引入的。

### 2.5 多任务支持

和 CosyVoice 3 一样，通过不同的 prompt 模板统一多任务：

| 任务 | 输入构造 | 特殊处理 |
|------|---------|---------|
| TTS | 文本 → 语音 | 基本模式 |
| 零样本克隆 | 文本 + 参考音频 → 语音 | 参考音频作为 prompt 前缀 |
| 跨语言克隆 | 文本(目标语言) + 参考音频(源语言) | 同上 |
| 指令控制 | 文本 + 指令 → 语音 | 指令 token 嵌入序列 |
| 流式 TTS | 同 TTS | 块级注意力 + 块级输出 |

## 3. 核心概念

### 3.1 块级因果注意力（Chunk-wise Causal Attention）

**一句话**：把"看完再说话"改成"看一块说一块"，每说完一块立即送下游，实现流式推理。

**类比**：传统因果注意力像是同声传译员必须听完一整段才开始翻译；块级注意力像是传译员每听完一句就翻译一句，实时输出。

**为什么重要**：这是 CosyVoice 2 的核心创新。没有这个机制，LLM-based TTS 就无法做到低延迟流式合成，在实际应用中（语音助手、实时对话）就不可用。

### 3.2 FSQ（Finite Scalar Quantization）

**一句话**：把连续向量的每个维度独立量化到一组固定值，拼接成离散编码，无需学习码本。

**类比**：VQ 像是用一本"词典"查最近似的词——词典质量决定一切，用得少的词会逐渐"失效"；FSQ 像是坐标量化——每个维度独立取整，不依赖词典，不会失效。

**为什么重要**：解决了 VQ 的码本坍缩问题，使得每帧只需 2 个 token 就能保留足够声学信息，降低了 LM 的序列长度和推理成本。

### 3.3 流式推理的交替混合机制

**定义**：流式模式下，文本 token 和语音 token 按 N:M 的固定比例交替排列。模型在接收到 N 个文本 token 后立即生成 M 个语音 token，通过 Filling Token 作为"请求信号"触发下一批文本输入。

**与块级注意力的关系**：块级因果注意力是底层的注意力掩码机制（限制当前块只能看到左侧已生成的块），交替混合序列是上层的输入输出调度策略。两者配合实现流式：交替混合决定"什么时候输出"，块级注意力决定"输出时能看到多少上下文"。

**为什么重要**：这是 CosyVoice 2 实现流式推理的核心技术组合，使得自回归 LM 无需等待完整输入即可开始生成。

---
## 4. 核心洞见

> 自回归 LLM 不需要放弃因果性也能做到流式推理——关键是重新定义"看到多少上下文才够"，而不是"怎么绕过因果性"。

这个洞见的实质：==流式和非流式不是架构选择，而是注意力范围的调节==。同一个模型、同一套参数，只要切换注意力模式（全局 vs 块级），就能在质量和延迟之间灵活切换。这对实际部署极其友好——一个模型覆盖所有场景。

## 5. 实验结果

### 5.1 流式 vs 非流式质量对比

| 模式 | 首包延迟 | WER(%) | SIM | NMOS |
|------|---------|--------|-----|------|
| 非流式 | ~2s | 3.81 | 0.782 | 4.05 |
| 流式(块=25帧) | ~400ms | 3.92 | 0.775 | 4.01 |
| 流式(块=10帧) | ~160ms | 4.35 | 0.761 | 3.92 |

流式模式 WER 略高（+0.11），SIM 略低（-0.007），但 NMOS 仅差 0.04——听感差异极小。首包延迟从 2 秒降到 400ms，接近实时。

### 5.2 零样本 TTS

| 模型 | WER(%) | SIM | NMOS |
|------|--------|-----|------|
| CosyVoice 1 | 5.42 | 0.721 | 3.85 |
| ==CosyVoice 2== | ==3.81== | ==0.782== | ==4.05== |
| VALL-E | 5.9 | 0.683 | - |

WER 比 1 代降低 30%，SIM 提升 8.5%。

### 5.3 跨语言克隆

| 设置 | WER(%) | SIM |
|------|--------|-----|
| 中文→英文 | 5.2 | 0.73 |
| 英文→中文 | 6.1 | 0.70 |

跨语言克隆可用但质量有下降，尤其目标语言为中文时 WER 偏高（中文的音素-文字对应更复杂）。

### 5.4 FSQ vs VQ 消融

| 量化方式          | 每帧 token | WER(%)   | SIM       | 码本利用率     |
| ------------- | -------- | -------- | --------- | --------- |
| VQ (4码本)      | 4        | 4.2      | 0.764     | 67%       |
| ==FSQ (2码本)== | ==2==    | ==3.81== | ==0.782== | ==~100%== |

FSQ 用一半的 token 数，效果反而更好。码本利用率从 67% 提升到接近 100%——VQ 有三分之一的码本向量根本没被用到。

### 5.5 流式 vs 非流式详细对比

- 流式模式（块=25帧）在零样本克隆任务上 WER 略高于非流式（+0.11%），SIM 略低（-0.007）
- NMOS 差异极小（4.01 vs 4.05），听感几乎无差别
- 块=10帧时质量下降更明显，但首包延迟可降至 ~160ms

- [?] 论文缺少对"为什么块=25帧就够了"的理论分析

## 6. AI审稿

**选题眼光**：好问题——LLM-based TTS 的流式推理是落地的硬障碍。但这个问题的紧迫性更多来自工程需求而非认知缺口，"怎么做流式"的答案其实可以预见。

**方法成熟度**：块级因果注意力是干净的工程方案，不是蛮力。FSQ 替代 VQ 也是合理且有理论基础的选择。模型合并替代 RLHF 是取巧——简单有效但上限不高。整体看，==架构设计有巧劲，训练策略有妥协==。

**实验诚意**：消融做得扎实——流式 vs 非流式、FSQ vs VQ、模型合并系数调参，每个设计选择都有数据支撑。但：
- 跨语言克隆的 WER 偏高（5-6%），论文没有分析失败模式
- 和竞品的对比主要靠对方论文数字，公平性存疑
- 没有人类评估（MOS 是他们自己标还是第三方标的？）

**写作功力**：方法部分清晰，图示直观。但缺少对块级注意力"为什么块=25帧就够了"的深入分析——是语音信号的局部性决定的？还是 LM 的泛化能力在起作用？

**判决**：==weak accept==——块级因果注意力是实用的工程贡献，FSQ 的选择有理论支撑。但作为学术论文，方法创新的深度不够——更像是把已知技术做了聪明的组合。

## 7. 启发

**迁移**：块级因果注意力的思路可以迁移到任何自回归生成的流式场景——视频生成、音乐生成、甚至代码补全。关键是找到"块大小"和"质量"的平衡点。

**混搭**：FSQ + 块级注意力可以和 CosyVoice 3 的 DPO 后训练结合——先用块级注意力做流式推理，再用 DPO 优化流式模式下的输出质量。CosyVoice 3 没有强调流式，但这个组合是有意义的。

**反转**：CosyVoice 2 假设"自回归是必须保留的"，但如果从零设计一个流式 TTS 系统，也许==非自回归 + 迭代细化==才是更自然的路径？扩散模型天生支持 early exit，不需要块级注意力这种 patch。
